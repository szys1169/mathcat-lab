# 当前数学研究智能体架构图解

更新日期：2026-09-03

## 0. 如何阅读本文

本文描述的是 `math-research-mvp` 当前实现，不把架构设想自动视为已完成能力。

- 蓝色：已实现的控制或服务组件；
- 绿色：经过信任门后可成为权威状态的对象；
- 黄色：外部输出或尚未验证的材料；
- 红色虚线：当前缺口或尚未完整落地的能力。

建议按“总览 → 研究闭环 → 验证层 → 可靠性 → 数据与接口 → 当前缺口”的顺序审阅。

### 各 crate 的职责

| Crate | 当前职责 | 不应承担的职责 |
|---|---|---|
| `domain` | 领域对象、状态枚举、任务与证据契约 | 数据库 I/O、调用模型 |
| `storage` | 权威状态、事务、Fact Gate、恢复、事件和 outbox | 数学推理、模型提示词 |
| `worker-runtime` | Codex CLI、Lean、Pantograph 和 mock 的受控执行 | 直接改 Fact 或项目终态 |
| `research-core` | 研究循环、规划、worker 调度、验证编排、发布编排 | 绕开 storage 直接提交可信事实 |
| `api` | HTTP、SSE、WebSocket、鉴权、OpenAPI | 自行实现第二套领域逻辑 |
| `cli` | 本地创建、运行、服务、发布、诊断入口 | 成为独立权威状态源 |

```mermaid
    Core->>DB: 原子提交 round / routes / tasks

        Core->>Worker: counterexample task + lease

    Core->>DB: 校验 lease / epoch / hash 后摄取

    Core->>Gate: adjudicated evidence + immutable snapshot

    alt 接受

    Core-->>Entry: 状态、事件、artifact、使用量
    Entry-->>Human: 展示或继续接受人工命令
```

本地 Worker、远程 Worker、Reviewer、Formalizer、Alignment Agent、Lean 和 Pantograph 都被纳入同一类受监督运行语义。

### 权威关系

```mermaid
flowchart TB
    P[(Project)] -->|revision| R[一致性版本]
    P -->|event cursor| E[可回放事件序列]
    P -->|active knowledge| F[Fact DAG]
```

项目 revision、event cursor 和领域状态变更在同一事务内提交，避免“数据库显示已完成但事件没有记录”或相反的分裂状态。

## 11. 崩溃恢复与迟到结果防护

```mermaid
flowchart TB
    CRASH[进程崩溃 / 重启] --> REC[Startup Reconciler]
    REC --> L1{是否有有效 checkpoint?}
    L1 -->|有| RESUME[从 checkpoint 恢复]
    L1 -->|无| L2{是否有已提交 envelope?}
    L2 -->|有| REPLAY[幂等重放摄取]
    L2 -->|无| RETRY[按有限重试策略重新排队]

    WATCH[周期 Watchdog] --> EXPIRE[扫描过期 lease / worker]
    EXPIRE --> EPOCH[提升 cancellation / route / task epoch]
    EPOCH --> RETRY

    LATE[旧 Worker 迟到结果] --> VALIDATE{lease token + epoch + hash}
    VALIDATE -->|匹配当前 attempt| INGEST[exactly-once ingestion]
    VALIDATE -->|旧 epoch 或无效 token| ARCHIVE[归档诊断，不改变当前状态]

    TAMPER[Artifact 缺失或 hash 不符] --> AUDIT[完整性审计]
    AUDIT --> QUAR[标记异常 / 修复事件 / 隔离]

    DUP[重复 active attempt<br/>或缺失 terminal event] --> REC
```

验证阶段重启时不会信任孤儿验证进程的结果，而是提升取消 epoch 后重新进行独立验证。

## 15. 当前最关键的审阅路径

如果只审阅五条链路，建议依次检查：

```mermaid
flowchart TB
    A[1. 原问题] --> B[Planner 是否覆盖所有 Goal]
    B --> C[2. Worker 输出是否被视为非可信 Candidate]
    C --> D[3. Verification 是否检查完整依赖、来源和语义对齐]
    D --> E[4. Fact Gate 是否是唯一权威入口]
    E --> F[5. Active Facts 是否真正联合闭合原问题]

    F -->|独立 coverage check| G{{Goal Closure Record}}
```

审阅时应把两个问题分开：

1. **局部事实是否可信？** 当前架构对此控制较强。
2. **这些可信事实是否完整回答原问题？** 当前由独立 Goal Completion Gate 控制，并可通过 closure API 审阅证据；复杂语义关系仍需要 reviewer 而非字符串猜测。
