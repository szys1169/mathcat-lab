## 1. 比较范围与结论边界

本文只比较两套系统真正重叠的能力：问题理解与完成判定、研究规划、例子与反例探索、递归证明、记忆、文献、证明组装、验证、长任务恢复和成果写作。Rust API、数据库等工程组件不直接与 Rethlas 的数学文本输出作错位比较。

结论同时依据：

- 当前 Rust 实现及架构审计；
- Rethlas 本地实现、生成端与验证端工作流；
- 两个同初始材料案例的实测结果；
- 当前版本的回归测试和产物。

目前只有两个严格同材料案例，因此可以可靠定位机制差距，但不足以宣称某一系统在所有数学领域都绝对更强。

## 2. 执行摘要

当前智能体已经具备比 Rethlas 更强的工程可信度底座：结构化任务、专业化并行角色、Fact DAG、来源准入、多个独立审查者、证据裁决、Lean/Pantograph 接口、快照回放、租约和恢复机制。这使它更适合成为可审计、可恢复、可扩展的研究基础设施。

但现阶段它尚未把这些底座稳定转化为更好的端到端数学成果。最关键的差距有四项：

1. **局部 Fact 通过不等于原问题完成。** 当前完成判定仍过度依赖结论文本规范化后的字面相等，不能可靠识别等价表述、蕴含关系或多个 Fact 联合闭合目标。Case 10 已完整证明原命题，却仍被标为 `partial_success`。
2. **规划很结构化，但数学上的自适应修补不足。** Rethlas 会持续围绕失败子目标生成多个分解、构造玩具例子、寻找反例、调用文献并递归证明，直到整篇蓝图通过；当前智能体更容易形成昂贵的多角色流水线，却在关键全局构造处停止。
3. **文献能力目前主要是可信度约束，不是完整检索能力。** 来源必须经过准入是正确的，但还缺少真正的检索、筛选、去重、全文读取、定理定位和适用性分析流水线。Rethlas 在这部分已经直接参与证明发现。
4. **验证层强，但验证对象和成本配置仍不理想。** 多审查者和形式化工具提高了局部可信度，却可能重复读取宽上下文、消耗大量 token，并且没有最终的“原命题覆盖审查”兜底。

一句话判断：**我们的系统更像可信的数学研究操作系统，Rethlas 当前更像高效完成单个开放式证明任务的研究员。要缩小差距，优先级应从继续增加验证器，转向全局闭合、自适应证明搜索和真实文献执行。**

## 3. 当前智能体的主要问题

### P0：会直接造成错误状态或任务无法完成的问题

#### 3.1 原问题完成判定不可靠

当前聚合逻辑的关键判断仍是规范化后的 statement 字面相等。它不能处理：

- 同一定理的等价改写；
- 一个更强结论蕴含目标；
- 多个已验证 Fact 联合推出目标；
- 目标含多个子结论，需要覆盖全部子目标；
- 定理成立，但证明依赖的假设版本与原问题不同。

这不是展示层问题，而是研究状态机的核心正确性问题。Case 10 中三个审查者均通过，Fact Gate 也接受了普遍命题，但项目仍为 `partial_success`，说明“事实准入”和“目标闭合”目前彼此脱节。

需要新增独立的 **Goal Completion Gate**：以目标结构、假设、量词、子目标覆盖、Fact 依赖图和必要时的模型判定共同决定完成状态，并保留机器可审计的闭合证据。

#### 3.2 全局数学覆盖能力不足

Case 03 中，当前智能体只得到嵌入维数 `e = 3` 的分类；Rethlas 得到了全部 `e` 的下界和递归 gluing 构造。说明当前系统能够验证局部正确结果，却未必能发现完成问题所需的全局结构。

根因不是单纯“模型不够强”，而是控制回路缺少以下强制动作：

- 当局部定理不足以覆盖目标时，自动识别最小缺口；
- 针对同一缺口生成多种分解，而非只扩展当前路线；
- 把小规模实验或玩具例子抽象成递推构造；
- 让失败路线产生新的数学约束，而不仅是失败记录；
- 对卡住的子目标递归启动专门证明回路；
- 在终止前执行整题覆盖审查。

#### 3.3 规划硬超时会损害长证明

规划阶段仍存在固定 20 分钟硬超时。复杂问题中，规划、文献和形式化工具的合理耗时差异很大，统一硬截止可能在即将形成有效方案时中断工作，也不能根据阶段进展决定续跑。

应改为软预算、心跳、阶段检查点和停滞判定相结合，并允许基于“是否产生新约束、新 Fact、新反例或新来源”动态续期。

### P1：显著限制研究质量、效率和可用性的问题

#### 3.4 文献研究尚未形成可执行闭环

当前已经正确引入来源信任边界：外部材料先进入 `reported_unverified`，经引用审查并与已接受 Fact 对齐后才能 `admitted`。但实际能力仍主要停留在 prompt 约束和账本记录，缺少：

- 面向原问题和卡点的查询生成；
- arXiv/期刊/作者主页等真实检索；
- 结果筛选、去重和版本识别；
- PDF/TeX/HTML 全文获取；
- 定理、假设、页码或编号定位；
- 引用定理与当前子目标的适用性检查；
- claim-source 对齐和矛盾来源处理。

结果是系统在“防止不可信引用进入事实层”上较强，但在“用文献真正推动证明发现”上明显弱于 Rethlas。

#### 3.5 多审查者带来较高重复成本

现有基准共 61 次调用，输入约 460.9 万 token、输出约 30.4 万 token，总墙钟约 3 小时 2 分。三个审查者和宽证明上下文是主要成本来源之一。

需要把验证上下文改为最小 proof slice，并按角色差异化：逻辑审查只看命题、依赖和证明；引用审查只看 claim-source 包；反例审查优先看量词、边界和计算证据。相同依赖和来源应缓存，不应让每个审查者重复读取完整历史。

#### 3.6 记忆很可靠，但未充分转化为策略优势

当前的 Fact、uncertainty、failure、snapshot 和 event 结构比 Rethlas 的文件记忆更可靠。不过“记录了什么”和“下一步因此怎么改变”仍有距离。例如失败路径虽然可保存，却未稳定触发：排除某类方案、提出相反构造、缩小参数范围或生成新的文献检索式。

应增加从记忆条目到 planner constraint 的显式编译步骤，让失败和不确定性成为下一轮规划的输入约束。

#### 3.7 Lean 接入强，但运行准备和失败恢复仍不完整

系统已经记录 Lean 版本、环境和回放信息，也有 Pantograph 搜索路径，这是相对 Rethlas 的明确优势。但仍缺少主动 warm-up、依赖预取、离线可用性检查和工具失败后的分级恢复。否则形式化验证可能在任务后段因环境问题成为不可预测瓶颈。

### P2：影响最终交付完整度的问题

#### 3.8 论文写作还没有进入可靠任务生命周期

受控 writer 已经限制只能使用 active facts、admitted sources 和引用白名单，也能报告 evidence gap；但它仍主要是直接后端调用，没有完整复用 V2 的 task contract、attempt、lease、heartbeat、result envelope 和恢复语义。

#### 3.9 发布流程不完整

当前发布主要通过 CLI，缺少统一 `/publish` API；集成测试偏重“有阻断项时不能发布”，缺少成功 ready-path 的完整 E2E。还缺少 LaTeX 编译、PDF 视觉检查、版本化产物和原子发布。

#### 3.10 Related Work 只是文本字段，不是研究证据产品

目前缺少历史时间线、主张—来源账本、同类结果对比矩阵、贡献定位以及独立的 related-work 审查。来源记录本身也较简化，无效来源草稿有时可能被丢弃，而不是保留拒绝原因和不确定性。

#### 3.11 写作准入规则可能过度约束

当前 writer 校验倾向要求 claim ledger 覆盖所有 active Fact，即使某些 Fact 与本论文无关。合理规则应是：所有写入论文的数学主张必须映射到 Fact；并非所有 Fact 都必须写入论文。

## 4. 与 Rethlas 相同能力的逐项比较

| 重叠能力 | 当前智能体 | Rethlas | 实际差距与判断 |
|---|---|---|---|
| 问题输入与完成契约 | 有结构化 Problem Contract、目标和状态机 | 始终围绕原始命题生成完整 blueprint，只在整体验证通过后结束 | 我们的架构表达更强，但当前完成聚合实现更弱；Rethlas 的终止条件更贴近“整题完成” |
| 全局规划与问题分解 | Route Generator → Reflection → Ranking → Supervisor，多路线可审计 | 自适应技能循环，生成多个子目标分解并根据失败随时改线 | 我们更结构化；Rethlas 的数学自适应更直接，Case 03 中效果更好 |
| 玩具例子和计算探索 | 有 explorer、计算证据和可回放产物 | 有专门 toy-example 技能，并把观察重新送回证明循环 | 我们的计算证据更可审计；Rethlas 更擅长把例子转化为全局猜想或构造 |
| 反例搜索 | 有 counterexample hunter 和反例审查角色 | 有反例技能，失败后继续调整命题或路线 | 能力相近；我们的证据链更强，Rethlas 的反馈闭环更短 |
| 并行与递归证明 | 多专业 worker 并行，任务结构完整 | 对失败计划的子目标递归启动证明子代理 | 我们工程并发更强；Rethlas 更紧贴当前数学瓶颈，值得吸收其按卡点递归的策略 |
| 研究记忆 | 数据库化 Fact DAG、失败、不确定性、事件、快照 | append-only 文件频道：子目标、证明步骤、反例、失败路径、重大决定等 | 我们在一致性、查询和恢复上明显更强；Rethlas 的语义频道更简单，更容易直接影响生成端 |
| 文献检索 | 有来源模型、信任状态、引用审查和准入门 | 主动搜索 arXiv 等，下载全文，读取定理和证明，检查适用性 | 当前 Rethlas 明显更强；我们有更好的信任底座，但缺少真正执行层 |
| 证明组装与修补 | 可从接受 Fact 生成候选论文，但全局组装仍弱 | 生成完整 informal proof blueprint，验证失败后反复整体修订 | Rethlas 当前更强，尤其是把局部结果组织为闭合证明 |
| 独立自然语言验证 | 多个独立 reviewer、引用审查、对抗审查和 evidence adjudicator | 独立验证服务按证明条目顺序检查，返回 correct/wrong 与修补建议 | 我们在独立性、审计和争议裁决上更强；Rethlas 更便宜直接，且修补建议立即回到完整证明 |
| 形式化验证 | Lean、版本固定、回放信息、Pantograph 搜索 | 主要依赖自然语言验证 | 我们明显领先，但形式化覆盖率和环境可靠性仍需提高 |
| 长任务恢复 | lease、heartbeat、attempt、checkpoint、outbox、reconciler、snapshot | 持久 Codex 会话、日志和文件记忆，可 resume 多轮 | 我们明显领先，尤其适合故障恢复和分布式执行 |
| 成果写作 | 受控 writer、Fact/source 白名单、evidence gap | 可形成接近论文的完整 verified blueprint，引用与结果叙述更成熟 | 我们可信边界更强；Rethlas 当前成品完整度更高 |
| 安全与权限 | workspace-write 边界、鉴权、受控工具和可审计状态变更 | 本地脚本使用 `--dangerously-bypass-approvals-and-sandbox` | 我们明显领先；Rethlas 的运行方式不应复制 |

## 5. 同初始材料实测结果

### Case 03：CI numerical semigroup pairs

| 项目 | 当前智能体 | Rethlas |
|---|---|---|
| 最终覆盖 | 只完成 `e = 3`，得到 `m >= 4` 的分类 | 完成全部 `e`，给出 `m >= 2^(e-1)` 下界和递归 gluing 构造 |
| 状态 | `needs_human_review` | 完整解答 |
| 评分 | 16.0 | 24.0 |

这个案例暴露的核心不是局部证明错误，而是系统没有从低维结果推进到一般递归构造。Rethlas 的多分解、递归证明和整题停止条件共同形成了优势。

### Case 10：RF relations

| 项目 | 当前智能体 | Rethlas |
|---|---|---|
| 数学结论 | 普遍命题通过三个 reviewer 并进入 Fact Gate | 完成普遍命题 |
| 系统状态 | 错误停在 `partial_success` | 完整解答 |
| 评分 | 25.0 | 25.0 |
| 额外证据 | 回放 11,935 个半群、211,777 对关系，0 mismatch；另有 Python 检查 | 来源和论文式表达更完整 |

数学效果在该案例中基本持平，但系统行为不同：我们的计算证据和审计链更强，Rethlas 的完成表达更好；我们的错误状态直接证明 Goal Completion Gate 是 P0，而非优化项。

### 成本观察

两个 Rust 基准合计：

- 61 次模型调用；
- 输入 4,608,873 token；
- 输出 303,712 token；
- 墙钟约 3 小时 2 分。

Case 10 中，Rethlas 报告约 52 分钟，当前智能体约 111.25 分钟。由于调用环境和成本口径不完全统一，这不能作为严格成本基准，但足以说明当前验证上下文和调度仍较重。

## 6. 差距的根因

两套系统最大的差异不是“一个有更多代理”，而是优化目标不同：

```text
当前智能体：候选结论 → 多层局部可信度审查 → Fact 准入 → 再尝试聚合
Rethlas：     原始问题 → 完整证明蓝图 → 整体检查 → 定向修补 → 直到原题闭合
```

当前智能体优先保证每个准入对象有来源、有证据、可回放，这个方向正确；但它缺少与 Fact Gate 同等严格的 Goal Completion Gate。Rethlas 的内部状态没有我们的严谨，却始终把“完整回答原题”作为唯一停止条件。

进一步说，Rethlas 的优势来自四个相互配合的机制：

1. 一个持续恢复的生成会话，保留问题级语境；
2. 明确的数学研究技能：玩具例子、反例、多种分解、关键失败识别；
3. 围绕失败子目标递归证明，而不是固定执行预先排好的角色流水线；
4. 真实文献检索和全文阅读直接进入证明发现。

我们的优势也来自四个系统性机制：

1. 类型化、事务化、可查询的研究状态；
2. 来源、事实、审查和发布之间的信任边界；
3. 形式化验证和计算证据回放；
4. 面向长任务和分布式 worker 的恢复能力。

因此正确方向不是把系统改造成 Rethlas，而是把 Rethlas 有效的数学控制循环放进现有可信底座。

## 7. 建议的修改顺序

### 第一阶段：先修正确性闭环

1. 实现 Goal Completion Gate，支持等价、蕴含、多 Fact 联合覆盖和假设匹配。
2. 增加 Case 10 回归：已接受的普遍定理必须将原项目推进为完成状态。
3. 增加最终 whole-proof coverage reviewer，其职责只判断原命题是否被完整回答，不重复局部 Fact 审查。
4. 把 planner 固定硬超时改为软预算、心跳、检查点和进展型续期。

### 第二阶段：补数学搜索闭环

1. 增加“玩具例子 → 规律猜测 → 一般构造”的显式策略。
2. 对关键未解子目标生成至少两种独立分解，并允许递归证明。
3. 把 failed path 和 uncertainty 编译为下一轮 planner constraints。
4. 当只得到特例时，强制检查归纳、递推、gluing、极值、紧性和分类完整性。
5. 在不降低安全边界的前提下保留问题级会话摘要，减少每轮重建上下文。

### 第三阶段：实现真正的文献能力

1. 查询生成、检索、筛选、去重、下载和全文抽取；
2. 定理编号、假设、页码和原文片段定位；
3. theorem-to-subgoal 适用性检查；
4. source version 和 provenance；
5. 拒绝来源也保留原因，不静默丢弃；
6. 继续沿用当前 `reported_unverified → admitted` 信任门，不能直接照搬 Rethlas 的宽松引用方式。

### 第四阶段：降成本并完善交付

1. reviewer 使用最小 proof slice 和差异化上下文；
2. 缓存公共依赖、来源和已验证引理；
3. writer 纳入标准 task/attempt/lease/heartbeat 生命周期；
4. 增加 `/publish`、成功发布 E2E、LaTeX 编译和 PDF QA；
5. claim ledger 改为覆盖“实际写入论文的主张”，而不是强迫写入所有 active Fact；
6. 完善 Related Work 的时间线、来源账本和贡献对比矩阵。

## 8. 不应从 Rethlas 复制的部分

- 不复制 `--dangerously-bypass-approvals-and-sandbox`；
- 不用单一自然语言 verifier 取代多证据和形式化验证；
- 不把文件追加日志作为唯一权威状态；
- 不使用无界等待替代心跳和恢复机制；
- 不允许外部文献未经准入直接成为 Fact；
- 不因追求整题闭合而降低命题、假设和来源的可审计性。

## 9. 最终判断

当前智能体与 Rethlas 的差距集中在“研究控制策略”而不是基础设施：

- **数学问题完成率：Rethlas 当前领先。** 它更擅长围绕同一原题持续修补、寻找全局构造并形成完整证明。
- **验证可信度：当前智能体领先。** 多审查、Fact Gate、形式化工具、计算回放和不可变证据链更完整。
- **文献实际执行：执行链已补齐，研究效果仍待更多样本证明。** 当前可用 live search、全文归档、版本/标识去重、定理定位和适用性审查，同时保留严格来源准入；本轮 Case 03/10 未产生 admitted source，不能据此宣称已在效果上追平 Rethlas。
- **可靠性与安全：当前智能体明显领先。** 任务恢复、事务状态和权限边界更适合长期运行。
- **最终论文产品：本地可信发布链已完成，论文研究表达仍需对比验证。** 当前已有幂等 publication 生命周期、版本化 LaTeX、受控编译和逐页 PDF QA；期刊模板、人工版式审阅与外部投稿仍不在范围内。

近期最有价值的工作不是继续横向增加角色，而是提升已经建立的三个纵向闭环的实际命中率：**从局部引理识别全局不变量、从失败卡点选择不过度收窄的新策略、让真实文献结果进入可准入事实**。只有端到端复测稳定闭合原题后，Rust 底座的优势才可表述为超过 Rethlas 的研究效果。
